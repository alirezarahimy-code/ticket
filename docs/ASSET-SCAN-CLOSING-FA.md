# شناسنامه‌ها — جمع‌بندی و پایان بحث

**نسخه:** ۱.۶۳.۱-r18

این سند همهٔ چیزی است که برای بستن این پرونده لازم است: چه چیزی ساخته شد، چه چیزی واقعاً کار می‌کند، چه چیزی خراب بود، و چرا.

---

## ۱. سه ایرادی که باز بود — پاسخ

### ایراد ۱: «استخراج محلی سرور، اطلاعات سرور را استخراج می‌کند»

**نه باگ — ماهیت کار.** برداشت محلی فقط سیستمِ میزبان PHP را می‌خواند. در r18 دکمهٔ جداگانهٔ آن با عنوان «استخراج محلی سرور سامانه» وجود داشت؛ در شاخهٔ فعلی آن گزینه از رابط کاربری برداشته شده است، چون سرور در فهرست است و باید از مسیر انتخاب سیستم‌ها و استخراج معمول خوانده شود.

### ایراد ۲: «به‌جای نام کامپیوتر، آی‌پی و مک‌آدرس تحویل می‌دهد»

**باگ بود — رفع شد و آزمون زنده دارد.**

```
bazresi-pc 192.168.1.65 00-1A-2B-3C-4D-5E  →  bazresi-pc
MAC تنها                                  →  «نام ثبت نشده»
MBA4-01 / PC-12AB34CD                     →  دست‌نخورده
```

### ایراد ۳: «استخراج از شبکه شکست می‌خورد»

**ریشه‌اش سه چیز بود، نه یکی:**

| # | علت | وضعیت |
|---|---|---|
| الف | فایل `tools/collect_via_smb.ps1` روی سرور **نبود** | بسته شد |
| ب | جمع‌آور خروجی را با کدگذاری **UTF-16** می‌نوشت | بسته شد |
| ج | نام دامنه در آزمون اشتباه بود (`CORP` به‌جای دامنهٔ واقعی) | بسته شد |

## ۲. یافتهٔ تعیین‌کننده — چرا هیچ‌کدام از کارهای قبلی جواب نمی‌داد

`domain_scan_remote_inventory_via_smb()` در **خط اول** چک می‌کند:

```php
$script = domain_scan_smb_script_path();
if ($problem === null && !is_file($script)) {
    $problem = 'اسکریپت tools/collect_via_smb.ps1 پیدا نشد.';
}
```

اگر فایل نبود، **هر مقصدی** خطا می‌گرفت — و پیام خطا هیچ اشاره‌ای به فایل نمی‌کرد. یعنی تمام کاری که برای روش SMB انجام شده بود، **هرگز روی سرور شما اجرا نشده بود.**

این توضیح می‌دهد چرا هر تغییری در r17 اثری نداشت.

## ۳. باگ کدگذاری — که کشف نشده بود

```powershell
powershell -File collect_server_inventory.ps1 > C:\ITSM\out.json
```

در Windows PowerShell 5.1 عملگر `>` فایل را **UTF-16LE با BOM** می‌نویسد. PHP آن را می‌خواند، `json_decode` شکست می‌خورد، و استخراج با این پیام رد می‌شد:

> «دادهٔ سخت‌افزاری قابل‌استفاده از سیستم مقصد دریافت نشد»

**در حالی که جمع‌آوری روی مقصد کامل و درست انجام شده بود.** سیستم فقط نمی‌توانست نتیجه را بخواند.

اضافه بر آن، `schtasks /tr` با کاراکتر `>` بدرفتاری می‌کند. پس این مسیر **حتی با فایل موجود هم کار نمی‌کرد**.

**اصلاح:** جمع‌آور پارامتر `-OutFile` گرفت و خودش فایل را با `UTF8NoBOM` می‌نویسد.

---

## ۴. لو رفتن رمز روی خط فرمان

نسخهٔ اول رمز را به `schtasks /p` می‌داد. خط فرمان هر فرآیند در Task Manager، WMI و Sysmon برای هر کاربری **خواناست**.

**اصلاح:** تسک با `Register-ScheduledTask` در یک نشست CIM ساخته می‌شود که اعتبارنامه در آن امن است. هیچ `schtasks.exe` نمانده و هیچ `-Pass` روی خط فرمان نیست.

---

## ۵. وقتی همهٔ پیش‌نیازها درست است

بخش ۵ ابزار تشخیص، چیزهایی را می‌سنجد که **با وجود** دامنه، رمز درست و فایروال خاموش هم می‌توانند شکسته باشند:

- `LocalAccountTokenFilterPolicy` — برای حساب دامنه‌ای بی‌اثر است، ولی باید تأیید شود
- سالم بودن سرویس `Winmgmt`
- **هویت واقعی پروسه** — دامنه‌ای است یا محلی؟

و بخش ۰.۵ هرگز نمی‌گوید «احتمالاً عضو دامنه نیستی» — خودش می‌سنجد و نام واقعی دامنه را چاپ می‌کند.

### آنچه آزموده **نشده**

این را صریح می‌گویم: **مسیر SMB روی ویندوز واقعی اجرا نشده.** نه در این محیط امکانش هست، نه قبلاً اتفاق افتاده. آزمون‌های بالا فقط متن اسکریپت‌ها را می‌سنجند تا باگ‌های شناخته‌شده برنگردند.

پس اگر پس از نصب، مسیر SMB باز هم شکست خورد، پیام دقیقی که می‌دهد را بفرستید — سه کد خطای تفکیک‌شده دارد:

| کد | معنی |
|---|---|
| `SMB_BAD_CREDENTIALS` | نام کاربری/رمز/دامنه غلط |
| `SMB_NOT_ADMIN` | وارد شد، ولی `C$` رد شد → ادمین محلی نیست |
| `SMB_TASK_FAILED` | ساخت یا اجرای تسک روی مقصد ناموفق |

```
✓ بازکردن \\BAZRESI-PC\C$    موفق — حساب روی این مقصد ادمین محلی است
✓ ساخت C:\ITSM               موفق — یعنی روش دوم SMB قابل اجراست
```
