## ۱. اصلاح گزارش قبلی

دریافت قبلی از مسیر `fetch_file` محتوای قابل استفاده برنگردانده بود و نتیجهٔ «فایل صفر بایت است» نادرست بود. دریافت مستقیم محتوای GitHub API این نتیجه را اصلاح کرد: فایل 8,244,183 بایت متن SQL دارد و یک dump کامل از نظر تعریف 82 جدول است. این گزارش مبنای جدید بررسی است.

## ۲. پوشش داده

در dump، جدول‌های عملیاتی و مرجع متعددی تعریف شده‌اند. درج داده در 28 statement دیده می‌شود؛ بخش عمدهٔ ردیف‌ها مربوط به تاریخچهٔ Logging/Audit است.

برای دامنهٔ Request Center:
- جدول `tickets` تعریف شده، اما هیچ statement درج داده برای آن در dump پیدا نشد.
- برای `ticket_messages`، `ticket_events`، `ticket_attachments` و `notifications` نیز دادهٔ اولیه درج نشده است.
- جدول‌های مرجع مانند `users`، `departments`، `categories`، `service_catalog`، `ola_policies` و `handling_units` دادهٔ محدودی دارند.

بنابراین این dump برای بررسی Schema و آماده‌سازی T01–T09 مفید است؛ اما برای T12 به‌تنهایی دادهٔ واقعی چرخهٔ درخواست ندارد. برای T12 باید در Clone مجزا fixtureهای کنترل‌شده و نقش‌های آزمایشی ساخته شوند و Legacy و شاخهٔ هدف روی دو Clone هم‌ساخت مقایسه شوند.

## ۳. تطبیق Schema جدول tickets با WorkflowService

تمام 32 ستون موجود در allowlist نوشتن `RequestCenterWorkflowService` در تعریف جدول `tickets` این dump موجودند. ستون‌های کلیدی وضعیت، تخصیص، SLA، OLA، لغو و تصمیم سوپروایزر نیز تعریف شده‌اند.

این نتیجه فقط تطبیق ساختاری است؛ اجرای query، صحت FKها در زمان import، و رفتار سرویس را اثبات نمی‌کند.

## ۴. وضعیت رجیستری Migration

در `schema_updates` تعداد 26 رکورد درج شده است. ثبت‌های نسخه‌های 1.62.76، 1.62.77، 1.62.79، 1.62.80، 1.62.82 و 1.62.88 دیده می‌شوند. Migrationهای 024 تا 031 و 033 ثبت شده‌اند؛ اما رکوردی برای `032-schema-updates-baseline.sql` وجود ندارد.

این یک اختلاف قابل پیگیری است، نه اثبات خرابی. فایل 032 در شاخهٔ اجرایی وجود دارد و طبق محتوای آن باید baseline رجیستری نسخهٔ 1.62.83 را با `INSERT IGNORE` ثبت کند. کد updater نیز اجرای Migration را بر اساس نام فایل به‌صورت سراسری تشخیص می‌دهد. در نتیجه، نبود رکورد 032 یعنی از روی این dump نمی‌توان گفت baseline migration اجرا شده است. پیش از هر retry باید وضعیت واقعی Clone و نتیجهٔ اجرای کنترل‌شدهٔ 032 ثبت شود؛ اجرای کور روی سامانهٔ عملیاتی ممنوع است.

## ۵. محدودیت ایمنی و محرمانگی

مخزن GitHub در زمان بررسی عمومی بوده و فایل SQL شامل رکورد حساب کاربری با hash گذرواژه و داده‌های Logging/Audit است. هیچ مقدار حساب، hash، نام شخص، متن لاگ یا دادهٔ قابل‌شناسایی در این گزارش بازنشر نمی‌شود.

تا وقتی مالک مخزن فایل را از دسترس عمومی خارج و دربارهٔ چرخش گذرواژهٔ حساب‌های داخل dump تصمیم نگرفته است، این dump باید دادهٔ محرمانه تلقی شود. حذف فایل از آخرین commit به‌تنهایی آن را از تاریخچهٔ Git و cloneهای قبلی پاک نمی‌کند؛ پاک‌سازی تاریخچه باید با برنامهٔ مستقل انجام شود.
