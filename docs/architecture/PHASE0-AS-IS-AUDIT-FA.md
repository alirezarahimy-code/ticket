## ۱. تصحیح یافته‌های نادرست گزارش مقدماتی

پیش از ارائه یافته‌های جدید، سه خطای گزارش قبلی و ریشه فنی آن‌ها ثبت می‌شود.

### ۱.۱. خطای روش گرپ — ریشه مشترک دو ادعای نادرست

الگوی `"a\|b"` به `grep -E` داده شده بود. در ERE دنباله `\|` یعنی کاراکتر
لفظی `|` نه عملگر «یا». بنابراین جستجو به‌دنبال رشته تحت‌اللفظی
`internal_note|is_internal` گشت و صفر برگرداند.

```
grep -ciE "internal_note\|is_internal" actions/ticket-actions.php   →  0   (نادرست)
grep -ciE "internal_note|is_internal"  actions/ticket-actions.php   →  12  (درست)
```

**نتیجه:** ادعای «یادداشت داخلی و ارجاع وجود ندارند» باطل است.

### ۱.۲. خطای تشخیص idempotency

گرپ فقط `IF NOT EXISTS` و `information_schema` را گارد می‌شمرد. شرط
`WHERE`، `INSERT IGNORE` و `DROP ... IF EXISTS` نادیده گرفته شدند.
«نبود گارد صریح» با «غیرتکرارپذیری» یکی گرفته شد. تحلیل اصلاح‌شده در بخش ۶.

### ۱.۳. برآورد بیش از حد خوش‌بینانه از تقویم

ادعا شد «تقویم مشترک از قبل وجود دارد». سنجش سطح API نشان می‌دهد
`ItsmJalali` موتور تاریخ و انتخابگر تاریخ است و هیچ قابلیت زمان‌بندی ندارد.
تحلیل اصلاح‌شده در بخش ۵.

## ۶. وضعیت مهاجرت‌ها

### ۶.۱. تحلیل اصلاح‌شده idempotency — پاسخ به بند ۳

| # | عبارت | تکرارپذیر واقعی | دلیل |
|---|---|---|---|
| ۰۰۵ | `UPDATE tickets SET status='waiting_user' WHERE status='pending'` | ✅ **بله** | شرط `WHERE` خودش گارد است؛ اجرای دوم صفر ردیف |
| ۰۱۱ | `UPDATE food_ticket_events ... WHERE ... AND (delivery_status IS NULL OR <> 'delivered')` | ✅ **بله** | شرط ردیف‌های تبدیل‌شده را کنار می‌گذارد؛ `COALESCE(delivered_at, NOW())` زمان اصلی را حفظ می‌کند |
| ۰۱۷ | `ALTER TABLE org_units DROP COLUMN IF EXISTS sort_order` | ✅ **بله** | گارد `IF EXISTS` |
| ۰۳۲ | `INSERT IGNORE INTO schema_updates ... ('1.62.83', ...)` ×۳۲ | ⚠️ فنی بله، معنایی مضر | بخش ۶.۲ |
| ۰۳۳ | `UPDATE log_issues i JOIN system_logs s ... WHERE i.context='system'` | ⚠️ مشروط | همگرا می‌شود، ولی اگر ردیف متناظر خودش `context='system'` باشد در اجرای بعد دوباره تطبیق می‌خورد (نوشتن بی‌اثر) |

**تصحیح جزئی نسبت به بند ۳ دستور:** مهاجرت ۰۱۷ از
`ADD COLUMN IF NOT EXISTS` استفاده نمی‌کند؛ کل فایل ۴ خط است و تنها عبارتش
`DROP COLUMN IF EXISTS sort_order` است — یعنی خودش یک مهاجرت از نوع
بازگرداندن تغییر قبلی است. نتیجه ارزیابی (تکرارپذیر) تغییر نمی‌کند.

**جمع‌بندی:** هر پنج مهاجرت عملاً تکرارپذیرند. ادعای قبلی «۵ مهاجرت
بدون گارد و غیرتکرارپذیر» **باطل و پس گرفته می‌شود**.

### ۶.۲. خطر واقعی مهاجرت ۰۳۲

کل فایل ۳۲ ردیف `INSERT IGNORE` با برچسب ثابت `'1.62.83'` برای
مهاجرت‌های ۰۰۱ تا ۰۳۱ است. سه مشکل:

۱. **برچسب نسخه تاریخی نادرست** — مهاجرت ۰۰۱ متعلق به ۱.۶۲.۸۳ نیست.
۲. **کلید یکتا روی زوج `(version, migration)`** — پس همان نام مهاجرت با
   نسخه دیگر ردیف جدید می‌سازد، نه تکراری. `INSERT IGNORE` این را نمی‌گیرد.
۳. **تعارض با ثبت‌کننده واقعی** — `system-update.php:381`
   `INSERT INTO schema_updates (version, migration)` را با **نسخه واقعی
   بسته** اجرا می‌کند. اگر ۰۳۲ هم اجرا شده باشد، رجیستری دو ردیف برای یک
   مهاجرت با دو نسخه متفاوت خواهد داشت.

**تصمیم تأییدشده:** ۰۳۲ به‌عنوان مهاجرت عادی استفاده نشود. در هیچ بسته
منتشرشده‌ای حضور ندارد.

### ۶.۳. سازوکار بازیابی — پاسخ به بند ۲

#### الف) پشتیبان‌گیری واقعاً انجام می‌شود

`system-update.php:344` پیش از حلقه مهاجرت:

```php
$backup = create_backup_bundle();                          // :344
$fileSnapshot = system_update_files_snapshot($backup['path'] ?? '');  // :346
```

`create_backup_bundle()` (`backup.php:185`) با
`mysqldump --single-transaction --routines --events --triggers` خروجی می‌گیرد.
اسنپشات ZIP فایل‌ها هم جداگانه گرفته می‌شود.

#### ب) بازیابی خودکار نیست

```
ارجاع به «restore» در system-update.php:  ۰
```

توابع `restore_sql_dump()` (`backup.php:422`) و `restore_upload_archive()`
(`backup.php:353`) وجود دارند ولی **فقط از رابط کاربری صفحه پشتیبان‌گیری
قابل فراخوانی‌اند**، نه از مسیر شکست به‌روزرسانی.

**تأیید هشدار شما: وجود Backup اثبات بازیابی نیست.** بازیابی کاملاً دستی و
وابسته به تصمیم اپراتور است.

#### ج) رفتار updater هنگام شکست — `system-update.php:363-383`

```php
foreach ($package['migrations'] as $migration) {
    if (system_update_migration_applied($version, $migration)) continue;
    try {
        backup_run_process($mysqlBinary, [...], $stage.'/migrations/'.$migration);
    } catch (RuntimeException $e) {
        throw new RuntimeException('مهاجرت '.$migration.' ناموفق بود (بقیهٔ تغییرات اعمال نشد): '.$detail);
    }
    db()->prepare('INSERT INTO schema_updates (version, migration) VALUES (?, ?)')->execute([$version, $migration]);
}
```

شش مشاهده:

۱. مهاجرت‌ها از طریق **باینری `mysql`** اجرا می‌شوند نه PDO ⇒ **خارج از هر
   تراکنش PHP**.
۲. حلقه در تراکنش پیچیده نشده ⇒ مهاجرت‌های موفق پیشین **اعمال‌شده باقی
   می‌مانند**.
۳. پیام خطا «بقیهٔ تغییرات اعمال نشد» دقیق است ولی یعنی سامانه در **وضعیت
   نیمه‌مهاجرت‌یافته** رها می‌شود.
۴. **ثبت در `schema_updates` پس از اجرا انجام می‌شود** — ترتیب درست است
   (مهاجرت اجرانشده ثبت نمی‌شود)، ولی اگر خود `INSERT` شکست بخورد مهاجرت
   اجرا شده و ثبت نشده است ⇒ اجرای دوباره در تلاش بعد.
۵. **فایل SQL ناموفق ممکن است نیمه‌اجرا شده باشد** — `mysql` CLI عبارات را
   پشت سر هم اجرا می‌کند؛ شکست عبارت پنجم، چهار عبارت قبلی را برنمی‌گرداند.
۶. **کپی فایل‌ها پس از مهاجرت‌هاست** (`:387`) ⇒ شکست مهاجرت یعنی کد قدیمی
   با اسکیمای جدید.

#### د) محدودیت ذاتی DDL

MySQL برای DDL **commit ضمنی** دارد؛ `ALTER TABLE` در تراکنش قابل بازگشت
نیست. طبقه‌بندی ۳۴ مهاجرت موجود:

| نوع | تعداد | امکان بازگشت |
|---|---|---|
| فقط DDL | ۱۶ | ❌ بازگشت تراکنشی ناممکن |
| فقط DML | ۴ | ⚠️ فقط با اسکریپت معکوس اختصاصی |
| DDL + DML | ۱۴ | ❌ پرریسک‌ترین |

**۳۰ مهاجرت از ۳۴ شامل DDL‌اند** ⇒ Rollback تراکنشی برای ۸۸٪ مسیر
موجود ذاتاً ناممکن است.

### ۶.۴. قیود ثبت مهاجرت جدید

- شماره آزاد بعدی: **۰۳۴**
- ترتیب اجرا: **آرایه `manifest.migrations`** (`system-update.php:363`)
- کلید یکتا: **`(version, migration)`**
- نسخه ثبت‌شده: **نسخه واقعی بسته**
- `requires_version` سخت‌گیرانه اعمال می‌شود (`system-update.php:119`)

## ۷. برنامه اصلاح زیرساخت

### ۷.۱. الزام Recovery Strategy برای هر مهاجرت

طبق بند ۲ دستور، هر مهاجرت جدید باید یکی از سه راهبرد را **صریحاً** اعلام کند:

| راهبرد | شرط کاربرد | الزام همراه |
|---|---|---|
| **Rollback امن** | فقط DML، یا DDL افزایشی خالص (`ADD COLUMN`) | اسکریپت معکوس `0NN-down.sql` + آزمون رفت‌وبرگشت |
| **Forward Fix** | DDL تخریبی یا تبدیل داده | مهاجرت اصلاحی از پیش نوشته و آزموده |
| **بازیابی از Backup** | تغییر ساختاری گسترده | آزمون بازیابی روی کپی واقعی + زمان تخمینی اعلام‌شده |

قالب پیشنهادی سرآیند هر فایل مهاجرت:

```sql
-- Migration: 034-request-appointments.sql
-- Version: 1.62.89
-- Type: DDL (additive)
-- Idempotent: yes (CREATE TABLE IF NOT EXISTS)
-- Recovery-Strategy: Rollback
-- Rollback-Script: migrations/034-request-appointments-down.sql
-- Verified-On: <تاریخ آزمون روی کپی DB>
```
