# راهنمای آزمون سنگین اجزای حیاتی سامانه — نسخه 1.62.88

## روش اجرا

این آزمون از GitHub Actions اجرا می‌شود و فقط روی شاخه‌ای که workflow از آن اجرا شده اثر دارد.

1. شاخه `test/1.62.88-critical-system-stress` را در GitHub باز کنید.
2. به زبانه **Actions** بروید.
3. workflow با نام **Critical System Stress — Full ITSM, Food, Traffic and CD/DVD** را انتخاب کنید.
4. روی **Run workflow** بزنید و همین شاخه را انتخاب کنید.
5. پس از پایان، Summary و Artifactهای هر دو job را دریافت کنید.

این workflow به‌صورت دستی اجرا می‌شود؛ با هر push یا روی سامانه زنده خودکار اجرا نمی‌شود.

## معماری ایمنی اجرا

- هر job یک MariaDB مستقل و دورریختنی ایجاد می‌کند.
- schema و داده‌های مصنوعی از ابتدا در همان دیتابیس ساخته می‌شوند.
- برنامه روی loopback اجرا می‌شود؛ هیچ آدرس production یا staging هدف قرار نمی‌گیرد.
- حساب‌ها، تیکت‌ها، سفارش‌ها، گروه‌ها و رسانه‌ها همگی synthetic هستند.
- هیچ فایل `config.php` نصب زنده، دیتابیس عملیاتی یا پوشه `storage/` نصب شما استفاده نمی‌شود.
- workflow اصلی فقط دو مجموعهٔ آزمون موجود را به‌صورت reusable اجرا می‌کند؛ منطق آزمون‌های تثبیت‌شده را کپی یا تضعیف نمی‌کند.
- خروجی هر job به‌صورت Artifact در GitHub Actions نگهداری می‌شود. گزارش ترکیبی PASS فقط وقتی صادر می‌شود که هر دو job موفق باشند.

## پوشش آزمون‌ها

### ۱. درخواست‌ها و گردش کار ITSM

- ورود حساب‌های آزمایشی و کنترل CSRF
- درخواست‌های هم‌زمان احراز هویت‌شده
- ایجاد و حل درخواست از مسیرهای POST واقعی برنامه
- کنترل شماره درخواست، یکتایی شماره و وضعیت نهایی در دیتابیس
- کنترل خطاهای PHP و SQL
- بررسی صفحات و APIهای اصلی

### ۲. کنترل تردد

- ثبت تردد آزمایشی از handler واقعی
- بازیابی رکورد از API
- نمایش صفحه چاپ بدون فراخوانی چاپگر
- ویرایش تردد و کنترل تاریخچه
- ثبت خروج
- حذف رکورد آزمایشی و تأیید حذف از API

### ۳. CD/DVD

- ثبت هم‌زمان رویدادهای CD/DVD
- بررسی وضعیت نهایی رسانه در دیتابیس
- ۶۰ رقابت هم‌زمان روی شماره‌های تکراری
- کنترل اینکه برای هر جفت رقابتی دقیقاً یک عملیات مجاز موفق شود
- کنترل عدم ایجاد رخدادهای متوالی ناسازگار برای یک شماره

### ۴. مدیریت غذا — آزمون مستقل و سنگین

- ۲۵۰ چرخهٔ مستقل ثبت سفارش، بازخوانی، لغو و بازخوانی مجدد
- ۲۵۰ کاربر هم‌زمان مدیریتی برای خواندن APIها
- ثبت گروهی ۲۵۰ سفارش و سپس لغو گروهی همان سفارش‌ها
- CRUD کاتالوگ غذا و منوی روز
- CRUD گروه غذایی و کارت مهمان
- بررسی نتایج پایدارشده در دیتابیس و لاگ سفارش‌ها

### ۵. سایر اجزا و کنترل‌های مشترک

- صفحات و APIهای داشبورد، کاربران، نقش‌ها، سازمان، دارایی، موجودی، دانشنامه، اعلان‌ها، SLA/OLA، مدیریت تغییر و مشکل، گزارش‌ها و سلامت سامانه
- بررسی مرزهای دسترسی و رد درخواست‌های غیرمجاز
- تست‌های Python، PHP و JavaScript موجود
- تست‌های DB smoke و cron مصنوعی
- آزمون خواندنی تاب‌آوری با ۲۵۰ نشست و ۳۲ PHP worker

## مواردی که این آزمون عمداً به دستگاه واقعی وصل نمی‌شود

- فایل Access/ODBC دستگاه تردد TENTER
- کارت‌خوان و سخت‌افزار حضور و غیاب
- چاپگر واقعی شبکه روی TCP 9100 یا صف چاپ Windows
- LDAP/Active Directory واقعی
- Task Scheduler و سرویس دائمی Windows روی سرور عملیاتی

این موارد باید در مرحلهٔ پذیرش سخت‌افزار/شبکه و با محیط آزمایشی همان تجهیزات بررسی شوند. موفقیت این workflow به‌تنهایی سلامت فیزیکی آن دستگاه‌ها را اثبات نمی‌کند.

## معیار قبولی

- هر دو job باید با وضعیت `success` پایان یابند.
- تعداد عملیات مورد انتظار باید با تعداد عملیات تأییدشده در دیتابیس برابر باشد.
- هیچ خطای غیرمنتظرهٔ PHP، SQL، API یا invariant نباید باقی بماند.
- در صورت شکست یک بخش، نتیجهٔ کل آزمون FAIL است؛ شکست‌ها نباید با کاهش تعداد تست یا نادیده‌گرفتن خطا پنهان شوند.

## ارتباط با دکمهٔ آیندهٔ «تست سلامت»

این آزمون سنگین برای اجرای دوره‌ای روی محیط آزمایشی است، نه دکمهٔ روزمره روی production. دکمهٔ آیندهٔ سلامت باید ابتدا فقط بررسی‌های خواندنی و کم‌خطر را اجرا کند و گزارش آخرین آزمون سنگین را جداگانه نمایش دهد.
