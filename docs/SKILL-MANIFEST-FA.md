## ۰. اعلام شفاف وضعیت حافظه

**من حافظهٔ پایدار رفتاری ندارم.** نمیتوانم سیستمپرامپت خودم را برای جلسههای آینده تغییر دهم یا چیزی را «همیشه بهصورت خودکار» در مدل ذخیره کنم. بنابراین:

- تمام ۳۱ مهارت این سند، **از لحاظ رفتار من، فقط در همین گفتگو فعالاند** و با پایان جلسه از بین میروند.
- در Skill Manifest وضعیت آنها دقیقاً **«موقت / فقط این جلسه»** ثبت شده است.
- آنچه **واقعاً پایدار** است، دو فایل متنی در مخزن Git است: این سند و `AGENTS.md`. اینها **سند** هستند، نه **حافظهٔ بارگذاریشوندهٔ خودکار**.
- برای فعالسازی دائمی، کاربر باید این دستورالعمل (یا ارجاع به آن) را در **سیستمپرامپت**، **فایل تنظیمات ابزار**، یا **حافظهٔ پایدار پروژه** (`AGENTS.md` / `CLAUDE.md` / `.cursor/rules/`) ذخیره کند. قرارداد `AGENTS.md` یک استاندارد باز و پرکاربرد برای همین منظور است.

> 🚫 **قید صداقت:** هرگز نباید گفته شود «مهارتها بهصورت دائمی نصب شدند»، مگر اینکه ابزار مصرفکنندهٔ `AGENTS.md` در جلسهٔ بعد عملاً آن را خوانده باشد و من بتوانم آن را تأیید کنم. تا آن لحظه، وضعیت رسمی = **موقت / فقط این جلسه**.

## ۲. پروتکل نصب (اعمالشده بر تکتک مهارتها)

برای هر مهارت، چهار گام زیر انجام شده و در بخش ۴/۵ ثبت شده است:

1. **تعریف رفتار قابل مشاهده** — کاری که بیرون از ذهن من قابل دیدن/اندازهگیری است.
2. **ساخت چکلیست** — ۲ تا ۵ شرط اجرایی بله/خیر.
3. **اتصال به گردشکار** — تعیین مرحلهٔ دقیق مصرف (درک / برنامهریزی / تولید / اجرا / تست / بازبینی / تحویل).
4. **معیار موفقیت** — شرطی که بگویم «این مهارت واقعاً اعمال شد».

گام پنجم، **آزمون خود قبل از تحویل**، توسط `tests/test_skill_manifest_static.py` بهصورت ماشینی انجام میشود.

## ۳. چکلیست گردشکار هفت مرحلهای

**گردشکار رسمی:** درک → برنامهریزی → تولید → اجرا → تست → بازبینی → تحویل

| # | مرحله | ورودی لازم (Gate ورود) | اقدامات | شرط خروج (Gate خروج) |
|---|---|---|---|---|
| ۱ | **درک** | درخواست کاربر + `git status` + ساختار فایلها | کشف فایلها، وابستگیها، الگوها، قراردادها؛ خواندن `README`/`docs/`؛ پرسیدن ابهامات | فهرست فایلهای درگیر و فرضهای صریح نوشته شده باشد |
| ۲ | **برنامهریزی** | خروجی مرحلهٔ ۱ | تجزیه به گامهای کوچک؛ تعیین ترتیب؛ شناسایی ریسک و مسیر بازگشت | لیست گامها + ریسکها + استراتژی rollback مشخص باشد |
| ۳ | **تولید** | خروجی مرحلهٔ ۲ | نوشتن کمینهترین تغییر هماهنگ چندفایله؛ رعایت سبک بومی پروژه | diff کوچک، خوانا و بدون تغییر نامرتبط باشد |
| ۴ | **اجرا** | خروجی مرحلهٔ ۳ | اجرای دستورات ایمن؛ مشاهدهٔ خروجی واقعی؛ ثبت خطا | دستورات اجرا و خروجیها مستند شده باشند |
| ۵ | **تست** | خروجی مرحلهٔ ۴ | تست واحد/ایستا/قرارداد؛ تأیید رفتار درست، نه فقط «اجرا شد» | حداقل یک اعتبارسنجی مستقل PASS کرده باشد |
| ۶ | **بازبینی** | خروجی مرحلهٔ ۵ | `git diff`؛ بررسی امنیت، رازها، سازگاری نسخه، عوارض جانبی | هیچ مورد بحرانی باقی نمانده باشد |
| ۷ | **تحویل** | خروجی مرحلهٔ ۶ | گزارش کوتاه: مهارتها / تستها / ریسکها / پیشنهادها + اعلام وضعیت حافظه | کاربر بداند چهchanged، چطور تست شد، چه ریسکی مانده |

**قانون توقف:** اگر در هر مرحله Gate خروج برقرار نشد، به مرحلهٔ بعد نرو — برگرد و اصلاح کن (S12).

## ۴. مهارتهای اصلی (S01–S23) — تعریف، چکلیست، معیار موفقیت

### S01 — تولید کد باکیفیت و متناسب با زمینهٔ پروژه
- **رفتار قابل مشاهده:** کدی مینویسم که از نظر نامگذاری، ساختار فایل، سبک کامنتگذاری و الگوهای معماری با فایلهای همجنس پروژه هماهنگ باشد؛ نه کدی «عمومی» که به زور به پروژه تحمیل شود.
- **چکلیست:**
  - [ ] قبل از نوشتن، حداقل ۲ فایل مشابه/مرتبط در همان پوشه خوانده شده است.
  - [ ] قرارداد نامگذاری پروژه (مثلاً `*-FA.md` در `docs/`، `test_*_static.py` در `tests/`) رعایت شده است.
  - [ ] هیچ وابستگی یا کتابخانهٔ جدیدی بدون توجیه اضافه نشده است.
  - [ ] کد شامل مدیریت خطای ورودیهای نامعتبر است.
- **اتصال به گردشکار:** تولید (و بازبینی).
- **معیار موفقیت:** diff نهایی شبیه کدی بهنظر برسد که یکی از نویسندگان فعلی پروژه نوشته باشد.

### S02 — درک کد و کدبیس ناشناخته
- **رفتار قابل مشاهده:** پیش از هر ادعا دربارهٔ سیستم، با ابزار فایلها، `git log`، مانیفستها و تستها را میخوانم و منبع حرفم را مشخص میکنم.
- **چکلیست:**
  - [ ] `ls`/`find`/`grep` روی پوشههای کلیدی اجرا شده است.
  - [ ] نقاط ورود (entry points) و جریان داده شناسایی شدهاند.
  - [ ] فایلهای پیکربندی و نسخه (`VERSION`, `manifest.json`, `ci.yml`) خوانده شدهاند.
  - [ ] بین «چیزی که دیدم» و «چیزی که حدس زدم» تمایز گذاشته شده است.
- **اتصال به گردشکار:** درک.
- **معیار موفقیت:** بتوانم بگویم هر تغییر روی کدام فایلها و قراردادها اثر میگذارد.

### S03 — اشکالزدایی سیستماتیک
- **رفتار قابل مشاهده:** خطا را بازتولید میکنم، پیام خطا را کامل میخوانم، یک فرضیه مینویسم، آن را با کمینهترین آزمایش رد یا تأیید میکنم و سپس اصلاح هدفمند انجام میدهم.
- **چکلیست:**
  - [ ] پیام خطای دقیق (نه خلاصهٔ ذهنی) ثبت شده است.
  - [ ] حداقل یک فرضیهٔ قابلآزمون نوشته شده است.
  - [ ] علت ریشهای پیدا شده، نه فقط علامت (symptom) پوشانده شده است.
  - [ ] یک تست/چک اضافه شده که از بازگشت همان باگ جلوگیری کند.
  - [ ] تغییر نهایی کوچکترین تغییر ممکن است.
- **اتصال به گردشکار:** اجرا و تست.
- **معیار موفقیت:** باگ در همان شرایط بازتولید دیگر رخ ندهد.

### S04 — تستنویسی و اعتبارسنجی
- **رفتار قابل مشاهده:** برای هر تغییر رفتاری، یک آزمون قابلماشین مینویسم/اجرا میکنم و «اجرا شد» را معادل «درست کار کرد» نمیدانم.
- **چکلیست:**
  - [ ] حداقل یک تست مرتبط وجود دارد یا نوشته شده است.
  - [ ] تست هم مسیر موفق و هم یک مسیر شکست/لبه را پوشش میدهد.
  - [ ] خروجی تست (PASS/FAIL) بهطور صریح گزارش شده است.
  - [ ] اگر ابزار اجرا موجود نبوده، صادقانه اعلام و جایگزین ایستا اجرا شده است.
- **اتصال به گردشکار:** تست.
- **معیار موفقیت:** نتیجهٔ تست قابل تکرار توسط کاربر باشد و رفتار درست را تأیید کند.

### S05 — بازآرایی کد بدون تغییر رفتار
- **رفتار قابل مشاهده:** تغییر ساختار میدهم، رفتار بیرونی را ثابت نگه میدارم و هر گام را جداگانه تست میکنم.
- **چکلیست:**
  - [ ] رفتار قبل از بازآرایی مستند/تست شده است.
  - [ ] بازآرایی و تغییر رفتار در یک کامیت قاطی نشدهاند.
  - [ ] تستهای موجود پس از هر گام همچنان PASS میکنند.
  - [ ] نامهای عمومی که تستها پین کردهاند، همراه تستها بهروز شدهاند.
- **اتصال به گردشکار:** تولید و بازبینی.
- **معیار موفقیت:** diff فقط سازماندهی را نشان دهد و سوئیت تست سبز بماند.

### S06 — فراخوانی ابزار و تعامل با محیط
- **رفتار قابل مشاهده:** ابزار مناسب را انتخاب میکنم، فراخوانیهای مستقل را موازی مکنم و خروجی هر ابزار را مبنای گام بعدی قرار میدهم.
- **چکلیست:**
  - [ ] کارهای مستقل در یک بلوک موازی اجرا شدهاند.
  - [ ] خروجی ابزار خوانده و تفسیر شده، نه نادیده گرفته شده است.
  - [ ] شکست ابزار با استراتژی جایگزین (fallback) پاسخ داده شده است.
- **اتصال به گردشکار:** همهٔ مراحل.
- **معیار موفقیت:** هیچ نتیجهای بدون پشتوانهٔ خروجی ابزار ادعا نشود.

### S07 — ویرایش چندفایله و هماهنگ بدون ناسازگاری
- **رفتار قابل مشاهده:** وقتی تغییر به چند فایل میرسد، فهرست دقیق فایلها را از قبل مینویسم و مطمئن میشوم ارجاعات متقابل (imports, paths, manifest) هم بهروز شوند.
- **چکلیست:**
  - [ ] فهرست فایلهای درگیر پیش از ویرایش تهیه شده است.
  - [ ] تمام ارجاعات به نام/مسیر تغییرکرده جستوجو و اصلاح شدهاند.
  - [ ] فایلهای قرارداد (`manifest.json`, `VERSION`, `README`) هماهنگ شدند.
  - [ ] `git diff --stat` با فهرست پیشبینیشده مطابقت دارد.
- **اتصال به گردشکار:** تولید.
- **معیار موفقیت:** پس از ویرایش، هیچ ارجاع شکستهای باقی نماند.

### S08 — مدیریت زمینه
- **رفتار قابل مشاهده:** اطلاعات مرتبط را نگه میدارم، طولانیها را خلاصه میکنم و دقیقاً هنگام نیاز بازیابی میکنم — نه اینکه همهچیز را دوباره بخوانم.
- **چکلیست:**
  - [ ] یافتههای کلیدی (نسخه، قراردادها، محدودیتها) بهصورت فشرده ثبت شدهاند.
  - [ ] هنگام نیاز به جزئیات، به فایل/بخش دقیق ارجاع داده شده است.
  - [ ] فرضهای قدیمی که با شواهد جدید نقض شدهاند، صریحاً اصلاح شدهاند.
- **اتصال به گردشکار:** درک و برنامهریزی.
- **معیار موفقیت:** در طول کار هیچ تناقضی بین ادعاهای قبلی و بعدی من نباشد.

### S09 — کار با Git و کنترل نسخهٔ ایمن
- **رفتار قابل مشاهده:** همیشه `git status` را قبل و بعد میبینم، فقط روی شاخهٔ مجاز کار میکنم و تغییرات را کوچک و قابلبازبینی نگه میدارم.
- **چکلیست:**
  - [ ] شاخهٔ فعلی و تمیزبودن درخت کاری بررسی شده است.
  - [ ] هیچ تغییری روی شاخهٔ دیگر یا با `reset --hard` / `push --force` انجام نشده است.
  - [ ] `git diff` پیش از اعلام اتمام بازبینی شده است.
  - [ ] فایلهای حساس/runtime طبق `.gitignore` از کامیت بیرون ماندهاند.
- **اتصال به گردشکار:** تولید و تحویل.
- **معیار موفقیت:** `$ git status` تغییرات را دقیقاً همان چیزی نشان دهد که گزارش کردم.

### S10 — اجرای دستورات ترمینال و فایل سیستم بهصورت قابلبازگشت

## ۵. مهارتهای مکمل کشفشده (C01–C08)

اینها از **شکافهای واقعی همین مخزن** کشف شدند، نه بهصورت انتزاعی. معیار پذیرش: مستقیماً کیفیت/ایمنی را بهتر کند، به چکلیست تبدیلپذیر باشد، با ابزارهای فعلی سازگار باشد و هزینهٔ غیرضروری اضافه نکند.

### C01 — مهاجرت امن و idempotent پایگاهداده
- **منبع کشف:** ۱۳ فایل در `migrations/`، ۴۲ فایل `upgrade-*.sql`، `schema_updates` در `docs/RELEASE-1.62.36-FA.md`، و هشدار صریح «هر فایل ارتقا را فقط یکبار اجرا کنید» در `README.md`. منابع معتبر خارجی: الگوی expand/migrate/contract و idempotency backfill ([2](https://www.harness.io/blog/zero-downtime-database-migrations-safe-schema-changes), [4](https://tech-champion.com/database/backward-compatible-database-migrations-the-expand-contract-pattern-for-zero-downtime-releases/), [5](https://arvucore.com/en/blog/database-migrations-strategies-for-production-environments/)).
- **رفتار قابل مشاهده:** هر SQL که مینویسم قابلاجرای مجدد باشد، ستونها را بهصورت افزایشی اضافه کند و قبل از هر `DROP`/`UPDATE` دستهای، backup و شمارندهٔ راستیآزمایی داشته باشد.
- **چکلیست:**
  - [ ] SQL با `IF NOT EXISTS` / `NOT EXISTS` / گuard روی `schema_updates` محافظت شده است.
  - [ ] هیچ `DROP COLUMN`/`RENAME` در همان گامِ مورداستفادهٔ نسخهٔ قبلی نیست (expand قبل از contract).
  - [ ] backfill بستهای/قابلازسرگیری است و کوئری شمارش ناسازگاری پس از آن صفر میشود.
  - [ ] مسیر rollback و backup قبل از اجرا مستند شده است.
- **اتصال به گردشکار:** تولید و تست.
- **معیار موفقیت:** اجرای دوبارهٔ همان migration هیچ ردیف اضافی و هیچ خطایی نسازد.

4. آیا بهجای «اجرا شد»، رفتار درست را تست/اعتبارسنجی کردهام؟ *(S04, S12)*
5. آیا `git diff` را برای امنیت، رازها و عوارض جانبی بازبینی کردهام؟ *(S13, S20, S23)*
6. آیا محدودیتها، تستهای انجامنشده و ریسکها را صادقانه گفتهام؟ *(S14, S19, C06)*
7. آیا نسخه/مستندات و قرارداد بستهها هماهنگاند؟ *(C02, C03)*
8. آیا وضعیت حافظه را دوباره اعلام کردهام؟ *(بخش ۰)*

## ۸. قواعد اجرایی همیشگی

- قبل از هر تغییر کد: **درک → برنامهریزی → تولید**.
- هیچوقت فقط به «اجرا شد» بسنده نکن؛ **رفتار درست را تأیید کن**.

- قبل از دستور مخرب/پرریسک **تأیید بگیر** و گزینهٔ ایمنتر پیشنهاد بده.
- هنگام نبود اطلاعات، **فرضها را صریح بنویس** و در صورت نیاز سؤال بپرس.
- در پایان هر کار مهم، **گزارش کوتاه** بده (قالب بخش ۷).
