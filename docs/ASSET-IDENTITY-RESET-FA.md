## ۱) پاسخ کوتاه به «۱۲۵ در برابر ۸۹»

سه علت مستقل روی هم افتاده بودند. هیچ‌کدام ربطی به دامنه، رمز یا فایروال نداشت.

### علت الف — کلید هویت، آدرس IP را می‌بلعید

تابع `asset_identity_key()` پیش از تشخیص IP، نام را نرمال می‌کرد. نرمال‌ساز نقطه را
جداکنندهٔ نام دامنه می‌دید، پس:

```
CLIENT-192.168.1.10   →  192
CLIENT-192.168.1.11   →  192
CLIENT-192.168.1.200  →  192
```

هر سه دستگاه یک هویت می‌گرفتند. نتیجه یا ادغام غلط بود یا — وقتی کلید یکتا
اجازه نمی‌داد — رکورد تازه ساخته می‌شد و شمارش بالا می‌رفت.

**اصلاح:** IP پیش از هر نرمال‌سازی‌ای شناسایی و دست‌نخورده برگردانده می‌شود.
پیشوند `CLIENT-`/`DOMAIN-` هم فقط وقتی حذف می‌شود که بقیه واقعاً یک نام باشد.

### علت ب — چهار مسیر درج، ستون `hostname_key` را ست نمی‌کردند

در MySQL مقدار `NULL` در یک ستون `UNIQUE` **یکتا شمرده نمی‌شود**. تا وقتی
`hostname_key` خالی می‌ماند، ایندکس یکتا هیچ کاری نمی‌کند و هر درج یک رکورد
تازه می‌سازد — حتی برای همان کامپیوتر با همان نام. این مهم‌ترین منبع تکرار بود.

**اصلاح:** هر مسیر درج فعال، کلید را همراه رکورد می‌نویسد.

### علت ج — جست‌وجو با `OR` رکورد بی‌ربط را می‌گرفت

```sql
WHERE (asset_tag = ? OR hostname = ? OR serial_number = ?)
```

تطابق روی **هر یک** از این سه کافی بود. اگر `asset_tag` با رکورد دیگری جور
می‌شد، شناسنامهٔ سیستم اشتباه به‌روز می‌شد و سیستم واقعی رکورد تازه می‌ساخت.

**اصلاح:** اولویت صریح و پله‌ای — سریال ← MAC ← نام ← `asset_tag`. هر پله جدا
پرسیده می‌شود و اولین تطابق برنده است.

## ۲) هویت دستگاه — پاسخ به «اگر سیستم عوض شود چه می‌شود؟»

این پرسش دو حالت دارد و پاسخ هر دو صریح است:

| وضعیت | چه می‌شود |
|---|---|
| **همان دستگاه، IP عوض شده** | همان شناسنامه به‌روز می‌شود. رکورد دوم ساخته **نمی‌شود**. |
| **همان دستگاه، ویندوز از نو نصب شده** | همان شناسنامه (سریال سخت‌افزار عوض نشده). |
| **دستگاه نو، جای دستگاه قدیمی** | شناسنامهٔ **تازه** ساخته می‌شود (سریال و MAC متفاوت است). |
| **همان دستگاه، نام عوض شده** | همان شناسنامه به‌روز می‌شود (سریال تشخیص می‌دهد). |

ترتیب تشخیص هویت:

1. **سریال سخت‌افزار** — پایدارترین شناسه. با تعویض نام، IP و نصب مجدد ویندوز
   تغییر نمی‌کند. سریال‌های بی‌معنی سازندگان (`TO BE FILLED BY O.E.M.`،
   `DEFAULT STRING`، `System Serial Number` و مانند اینها) نادیده گرفته می‌شوند.
2. **MAC آداپتور اصلی** — وقتی سریال خالی یا بی‌معنی است (ماشین مجازی، برخی برندها).
3. **نام کامپیوتر** — وقتی هیچ‌کدام نبود.

**آدرس IP هرگز بخشی از هویت نیست.** دلیلش ساده است: در شبکهٔ DHCP آدرس عوض
می‌شود. اگر هویت روی IP سوار شود، همان دستگاه با IP تازه رکورد دوم می‌سازد —
و این دقیقاً همان چیزی است که شمارش را از ۸۹ به ۱۲۵ برد.

## ۳) دکمهٔ ریست (درخواست شما)

### از پنل

**تنظیمات → کارت «ریست شناسنامه‌ها»** (فقط برای مدیر اصلی دیده می‌شود).

- کادر تأیید باید عیناً کلمهٔ **ریست** را داشته باشد. یک کلیک اشتباهی کافی نیست.
- پیش از حذف، بکاپ کامل JSON در `storage/asset-reset/` ساخته می‌شود.
- **اگر نوشتن بکاپ شکست بخورد، هیچ رکوردی حذف نمی‌شود.**
- حذف در یک تراکنش است؛ خطای میانهٔ کار همه‌چیز را برمی‌گرداند.
- بعد از ریست، شمارش صفر می‌شود و از «اسکن دامنه» می‌توانید از نو پرش کنید.

**چه چیزی پاک می‌شود:** شناسنامه‌ها، پروفایل‌ها، تاریخچهٔ استخراج، ماژول‌های
حافظه، دیسک‌ها، کارت گرافیک، لوازم جانبی، نرم‌افزارهای ثبت‌شده.

**چه چیزی می‌ماند:** کاربران، درخواست‌ها، گروه‌های غذایی، تنظیمات سامانه، بکاپ‌ها.

### از خط فرمان

```
C:\xampp\php\php.exe tools\asset_reset.php
C:\xampp\php\php.exe tools\asset_reset.php --apply
```

دستور اول فقط گزارش می‌دهد و هیچ چیزی را تغییر نمی‌دهد. برای بازگردانی:

```
C:\xampp\php\php.exe tools\asset_reset_restore.php
C:\xampp\php\php.exe tools\asset_reset_restore.php <نام-فایل-بکاپ> --apply
```

## ۴) راه پیشنهادی — اول ادغام، بعد ریست

ریست همه‌چیز را پاک می‌کند و تاریخچه را از دست می‌دهید. اگر فقط می‌خواهید
۱۲۵ به ۸۹ برسد، **اول این را امتحان کنید**:

```
C:\xampp\php\php.exe tools\asset_dedupe.php
```

فقط گزارش می‌دهد: چند گروه تکراری هست، از روی نام چند گروه و از روی سریال چند
گروه، و در هر گروه کدام رکورد می‌ماند. اگر اعداد منطقی بود:

```
C:\xampp\php\php.exe tools\asset_dedupe.php --apply
```

رکورد با کمترین `id` می‌ماند، فیلدهای خالی‌اش از روی رکوردهای تکراری پر می‌شود،
وابستگی‌ها (تاریخچه، درخواست‌ها، پروفایل) منتقل می‌شوند، و رکوردهای اضافی حذف
می‌شوند. **بکاپ در جدول `asset_dedupe_backup_*` می‌ماند.**

تازه در r19: این ابزار دیگر فقط بر اساس **نام** گروه‌بندی نمی‌کند. بر اساس
**سریال سخت‌افزار** هم می‌کند — پس رکوردهایی که برای یک دستگاه با نام‌های
مختلف ساخته شده‌اند هم پیدا می‌شوند. این همان چیزی است که ۳۶ رکورد اضافه را
پیدا می‌کند.

اگر مطمئن شدید، ایندکس یکتا را هم فعال کنید تا دیگر تکرار ممکن نباشد:

```
C:\xampp\php\php.exe tools\asset_dedupe.php --apply --enforce
```

## ۵) چه چیزی آزموده شد و چه چیزی نه

**آزموده شد (آفلاین، ۲۸ بررسی):** گروه‌بندی union-find شامل زنجیرهٔ نام+سریال،
دست‌نخورده ماندن IP، اولویت سریال/MAC، رد شدن سریال‌های بی‌معنی، وجود ستون
`hostname_key` در هر مسیر درج، پیش‌فرض «بدون تغییر» در ابزار ریست، و بکاپ/تراکنش.
با شبیه‌سازی ۱۲۵ رکورد و ۳۶ جفت تکرار، خروجی ۸۹ شد.

**آزموده نشد:** اجرای واقعی روی MySQL و ویندوز. این محیط MySQL ندارد. منطق
گروه‌بندی و SQL با شبیه‌سازی سنجیده شد، ولی پیش از `--apply` روی دادهٔ واقعی،
دستور گزارش (بدون سوییچ) را بزنید و اعداد را ببینید.

**بدون مهاجرت، بدون تغییر جدول.** نصب فقط جای‌گزینی فایل است.
